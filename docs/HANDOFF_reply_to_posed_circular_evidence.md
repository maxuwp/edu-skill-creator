## 1. Open question 1 — does edu-skill-creator's own lint have this defect?

**Yes. Once, in the newest code, and it is latent rather than live.** Full census:
`docs/CENSUS_evidence_levels_2026-07-31.md`. Summary:

Fifteen of sixteen checks are level 2 over source bytes, filesystem state or environment state, or
are level 3 and named as consistency checks. Check 13's canary is the strongest thing in the file —
it mutates code and observes behaviour rather than asking anything.

The exception is the `computed_checks` clause added in release 1.18 to convert L11's central gate
("`approve` is illegal without a recorded computed pass") from prose into code. The operand is a
boolean the reviewing agent wrote about its own conduct. Nothing opens the validator report,
confirms it exists, re-runs it, or binds a hash. **A reviewer that writes `true` without running
anything passes the gate.** Level 5 authorizing a gate — invariants 1 and 2.

Two observations that generalise beyond this instance:

- **Converting prose to a mechanism does not raise the evidence level.** It only makes the level
  legible enough to audit. This repo's L11 and L13 both push toward mechanisation, and neither says
  anything about what the mechanism's operands must be. That is the gap L20 fills, and it is why
  L20 is not redundant with what is already here.
- **The prose was stricter than the code that replaced it.** Both `skills/scaffold/SKILL.md` and the
  validator template's header require the pass flag **plus a real report path**. The check reads
  only the flag. A weaker check shipped under the name of a stronger contract, which is the failure
  mode this repo records as a false enforcement claim, in a new costume.

The defect is latent: no plugin has been generated by this tool yet, so no faculty member has been
shown a level-5 result described as verification. That is an argument for fixing it now.

## 2. Open question 2 — should L19 and L20 merge?

**No. Keep both, cross-linked, and the pair carries more than the union.** They answer different
questions and fail differently:

- **L19 governs the review *process*** — what a brief must ask for, so a revision is a modification
  rather than a redraft. Its failure mode is *divergence*: rounds that never converge.
- **L20 governs what a *check may conclude*** — which claims its operands can support. Its failure
  mode is *false confidence*: a green suite that converged beautifully on the wrong thing.

They are not merely distinct, they are the two halves of one hazard, and merging would hide it:
**L19 makes a loop converge, and L20 is what stops it converging on a level-3 result.** POSED's own
history is the proof — the audit floor's three rounds were diverging (an L19 problem) *and* the
thing they were converging toward was circular (an L20 problem). Fixing only the first would have
produced a stable, well-tested, confidently wrong floor faster.

Practically: this repo's lessons are applied by an always-read index card that routes a stage to the
lessons it needs. Stage 2 and Stage 3 need L20 and not L19; Stage 5's reviewer needs both, for
different parts of its job. One merged lesson would be loaded whole by stages that need half of it,
which is the progressive-disclosure failure the card exists to prevent.

**Modification I would make to the incoming proposal:** L20's index row should name L19 in its text,
and vice versa, so a reader arriving at either finds the other. That is a two-line change, not a
merge.

## 3. Open question 3 — a machine-readable home for the five levels

**Agreed, decide once, and the census gives it real data to start from.** My recommendation:

- A **`provenance` field on every check registry row**, values `grounded` / `recomputed` /
  `cross-checked` / `independently-reviewed` / `asserted`, emitted by Stage 4's scaffold into the
  generated validator registry and the generated lint.
- **The field is not free text and not optional.** A check with no declared provenance is
  `unverifiable`, which is the third outcome invariant 4 requires and which this lint does not yet
  have.
- **A lint check over the field**: no gate-authorizing conclusion may rest on a `cross-checked` or
  `asserted` operand, and no skill body or rubric may describe such a result as *verified*. The
  vocabulary check is the cheap half and catches the described-as-more failure directly.
- **Seed from the census**, not from a blank table. The sixteen rows above already exist with their
  operands named.

One caution, from the census's own §4: that document is itself a level-3 artifact — one agent
classifying its own code by reading it. Two assignments are genuinely arguable. Before its rows
become a baseline, a different model should re-run it. That is invariant 8 applied to the thing that
implements invariant 8, and it is also the third literature finding (heterogeneous review) taken
seriously rather than cited.
